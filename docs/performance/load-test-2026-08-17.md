# Load Test - 2026-08-17

## Scope

This test characterizes the local, single-instance Docker Compose stack. It is not a production-capacity claim or a user-count estimate.

The workload used k6 1.0.0 and the real API, PostgreSQL database, local Sentence Transformers model, Hugging Face Inference API, persisted log files, and Jaeger tracing. Each virtual user paused for 0.5-1.5 seconds between actions. The request mix was:

- 45% `GET /drive/folders?page=1&pageSize=50`
- 25% `GET /admin/logs?page=1&pageSize=50`
- 25% `GET /search?query=What%20is%20Amanah%20Drive%3F&topK=5`
- 5% `POST /chat` with the same question and a new conversation

One `POST /auth/login` call ran during each scenario setup. The administrator's plaintext password was not available and changing credentials was out of scope, so the measured runs used an intentionally invalid, nonexistent account for that call and expected `401`. Authenticated requests used a short-lived JWT generated locally with the development signing key and the real administrator subject; the token was not written to the repository or result files. Consequently, the reported login timing does not measure the Argon2 password-verification path. The k6 script supports a real login when `LOGIN_EMAIL` and `LOGIN_PASSWORD` are supplied.

## Environment

- Host: Windows 11 Pro, Intel Core i7-11800H, 16 logical processors, 16 GB RAM
- Docker memory limit visible to containers: 7.647 GiB
- Dataset at test start: 2 files, 1 searchable document chunk, 7 conversations
- Test duration: 30 seconds per level, with the one-minute AI rate-limit window allowed to reset between levels
- k6: `grafana/k6:1.0.0`
- Query traffic reached the API over the Compose network at `http://api:8080`

The workload is reproducible from [infra/load-tests/amanah-drive.js](../../infra/load-tests/amanah-drive.js). Example invocation:

```powershell
docker run --rm --network amanah-drive_default `
  -e BASE_URL=http://api:8080 `
  -e ACCESS_TOKEN=<short-lived-token> `
  -e VUS=1 `
  -e DURATION=30s `
  -e SEARCH_QUERY="What is Amanah Drive?" `
  -v "${PWD}/infra/load-tests:/scripts:ro" `
  grafana/k6:1.0.0 run /scripts/amanah-drive.js
```

## Trace Analysis

The first throughput boundary was the configured shared search/chat limiter: 20 requests per client IP per one-minute fixed window. At 2 VUs the stack served 20 search/chat requests and rejected the next 3; at 4 VUs it rejected 19. This is intentional load shedding, not service failure.

Jaeger trace `63753962309860352497de0b7f6be6ca` captured the slowest accepted chat request in the 4-VU run:

| Span | Duration | Share of API request |
| --- | ---: | ---: |
| API `POST /chat` | 929.88 ms | 100% |
| API to AI service `/embed` | 10.83 ms | 1.2% |
| API to AI service `/rag/answer` | 907.27 ms | 97.6% |
| AI service to Hugging Face | 894.90 ms | 96.2% |

The dominant chat cost was the real external Hugging Face generation call. Local retrieval, persistence, and request handling occupied the remaining small part of the trace.

Jaeger trace `f9718e575b4c8e1be1565e14971d65ab` captured the slowest accepted search request in the same run:

| Span | Duration | Share of API request |
| --- | ---: | ---: |
| API `GET /search` | 72.42 ms | 100% |
| API to AI service `/embed` | 43.22 ms | 59.7% |
| AI service `/embed` | 40.56 ms | 56.0% |

The local embedding model was the largest visible search span. The uninstrumented remainder includes the pgvector query and API response work. With one stored chunk and a 72 ms worst accepted request, this run does not provide evidence of a database bottleneck. The AI service's sampled CPU peak is consistent with embedding bursts, but accepted search latency remained below 66 ms at p99.

## Decision

No application change was made. The measured chat bottleneck is an external model call, and the first error boundary is the deliberately configured abuse limit. Increasing the limiter, adding caching, changing model behavior, or adding a vector index would alter product or operational policy without evidence that it fixes a defect in this workload. There is therefore no honest before/after optimization comparison for this run.

## Limitations And Next Steps

- The 30-second levels characterize short interactive bursts, not sustained load or soak behavior.
- The dataset is too small to characterize pgvector performance as document count grows.
- The source IP represents one client behind the Compose network. The per-IP limiter is expected to constrain this workload before infrastructure saturation.
- Nine successful chat requests created nine persisted conversations, leaving 16 total after the test.
- Successful login and Argon2 verification need a separate run with an explicitly supplied test credential.
- A larger-data follow-up should seed a controlled chunk count, add database spans or query timing, and test search independently below the configured limiter.
- A longer chat test would need an agreed Hugging Face quota/cost budget and enough samples for meaningful p95/p99 values.
